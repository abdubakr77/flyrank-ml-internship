Content Refresh Prioritization: Does a Learned Model Beat a Hand-Written Rule?

Abdullah Bakr · abdubakr77.github.io

Abstract

Content teams need to know which pages to review first when review time is limited, but it is unclear whether a hand-written prioritization rule is good enough or whether a learned model is worth the added complexity. This paper builds a client-grouped, leakage-checked Random Forest classifier on a 30,000-page content dataset and compares it against a hand-written staleness-and-visibility baseline on the exact same test split. The model improved Precision@50 from 0.52 to 0.80 over the baseline. Permutation importance showed the model relies almost entirely on two signals, content age and visibility, with the staleness signal the baseline weighted heavily contributing near zero. The result is scoped as an observed, decision-support finding on one dataset and one split, not a causal or universal claim about rules versus models.

1. Introduction

A recurring problem inside FlyRank's own content workflow is prioritization: given hundreds of pages and limited reviewer time each week, which pages should a content team look at first? A simple hand-written rule, flag pages that are both stale and still visible, is fast to build and easy to explain, but it is not obvious whether it captures the real pattern or misses interactions a more flexible model could find.

This paper treats that question directly: build a scoring model for the same task, validate it honestly, and compare it against the rule on the same data and the same metric, rather than reporting either number in isolation.

2. Data

This study uses the local cached starter release: 30,000 pseudonymized content pages across 44 columns, covering search performance (Google Search Console fields), engagement (GA4-derived fields), and content metadata (age, word count, content type).

What was excluded, and why

  • AI-referral and engagement columns (ai_chatgpt, scroll_events, and similar) were excluded from the feature set. An earlier data-contract audit found these columns roughly 69% populated, not missing, but they measure a different signal (AI-referral traffic) than the refresh-priority question this model targets.
  • Client and content identifiers were used only as grouping keys for the train/test split, never as model features, to avoid the model memorizing client identity instead of learning generalizable signal.
No client names, private URLs, or query-level data appear anywhere in this paper. All figures reference anonymized, aggregate statistics only.

3. Methodology

Label

trend_direction == 'down' (binary), an outcome already present in the dataset, derived from a 30-day-vs-previous-30-day impression comparison. This is an observed label, not a rule defined for this study.

Features

15 features were used: search volume, competition, CPC, word count, 90-day impressions/clicks/sessions/engaged sessions/scroll events, content age, days since last update, CTR, average position, engagement rate, and scroll rate. trend_pct was deliberately excluded, it is derived from the same window that defines the label, and including it would constitute direct label leakage.

Baseline

A hand-written rule weighting visibility (log-scaled 90-day impressions) at 70% and staleness (days since last update) at 30%. This weighting followed a signal audit: visibility showed a consistent, monotonic relationship with decline (CONFIRMED), while staleness alone showed an inconsistent pattern across buckets (MIXED), so the rule leaned on the more reliable signal.

Model

A Random Forest classifier (200 trees, max depth 8), chosen because it can capture interactions between signals, such as staleness only mattering when visibility is also high, that a single linear rule cannot represent.

Validation design

Both the baseline and the model were evaluated with a client-grouped split (GroupShuffleSplit by client ID), not a random row split. This choice was tested directly: a naive random split inflated Precision@50 to 0.96 due to 27 clients appearing in both train and test; the honest grouped split, with zero client overlap, reports 0.80. The gap between those two numbers is the size of the leakage risk a casual split would have hidden.

Leakage checks

  • Confirmed trend_pct excluded from all features.
  • Confirmed no client or content identifiers used as model inputs.
  • Flagged, but not yet fully resolved: content_age_days, the strongest feature by permutation importance, was not explicitly checked for correlation with the 30-day window used to define the label. Very new content could mechanically show inflated trend signals unrelated to genuine decline.

5. Limitations

  • Trained and validated on a single dataset snapshot; not yet tested across multiple months or the full warehouse release.
  • content_age_days needs a follow-up correlation check against the label's time window before being treated as a fully clean signal.
  • Roughly a third of top-ranked REVIEW pages are trending stable or up, not down. A REVIEW flag is a prioritization signal, not a confirmed diagnosis.
  • This work shows correlation between signals and decline, not causation. It does not establish that refreshing a page causes traffic recovery.
All claims in this paper use observed, measured, and decision-support language. No causal or universal claims are made.

6. Ranked Recommendations

The trained model's output was converted into a weekly content action playbook:

  • REVIEW (top 20% score, stale-or-visible reason code): a content editor opens the page and manually confirms the trend before acting.
  • MONITOR (everything else): no action this cycle, re-scored next run.

Before acting, a human must:

  • Confirm the page is genuinely trending down, not just score-ranked, since the score can surface stable or improving pages.
  • Check whether the page belongs to a contractually sensitive client relationship.
  • Verify the page is not intentionally low-traffic by design.

Never automate without human sign-off:

  • Rewriting or deleting content based on the score alone.
  • Applying this model to a client not represented in the training data's mix.
  • Using REVIEW/MONITOR as a public-facing quality certification.

Retrain or re-audit triggers:

  • Precision@50 on a fresh sample drops meaningfully below 0.80.
  • The share of REVIEW pages actually declining falls well below the ~65% observed here.
  • A new content type, client segment, or major site redesign is introduced.
  • More than 3 months since the last validation, as a routine check.
